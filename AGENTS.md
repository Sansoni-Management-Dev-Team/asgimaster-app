# mlai-sansoni — Agent standards

Sansoni member app. This is an npm workspaces monorepo:

- `apps/mobile` is the native iOS and Android app. Expo + React Native + TypeScript.
- `apps/api` is the backend. A TypeScript Hono server in a container.
- `infra` is the Terragrunt for the AWS resources the API runs on. Sansoni DevOps (Rodney) maintains it.

The repository is hosted at `Sansoni-Management-Dev-Team/asgimaster-app`. AWS resources are defined in `infra/`, which was copied from Sansoni's `devops-infrastructure-asgi-app` repository.

Run `npm install` from the repository root only. There is one lockfile, at the root.

## Read this first

Expo changes often. Before writing any code, read the exact versioned docs for the SDK this repo uses: https://docs.expo.dev/versions/v57.0.0/

## Mobile stack (decided at scaffold time)

Everything in this section is relative to `apps/mobile`.

- Runtime: Expo SDK 57, React Native 0.86, React 19.2. New Architecture and React Compiler are on.
- Native builds: Continuous Native Generation. The `ios/` and `android/` folders are generated by `expo prebuild` and are gitignored. Do not commit them. Change native config through `app.json` and config plugins.
- Language: TypeScript, strict mode on. Path aliases: `@/*` maps to `src/*`, `@/assets/*` maps to `assets/*`.
- Routing: Expo Router (file based) under `src/app`. Typed routes are on.
- Server state: TanStack Query.
- Client state: Zustand.
- Styling: NativeWind 4 (Tailwind utility classes). Shared design tokens live in `tailwind.config.js`.
- Testing: Jest with jest-expo and React Native Testing Library. End to end with Maestro.
- Lint and format: ESLint flat config (eslint-config-expo) with Prettier.

## API and infrastructure

- API: Hono on Node 24, TypeScript strict, ES modules. Tests use the Node test runner through `tsx`. The container is built from the repository root with `apps/api/Dockerfile`.
- The load balancer target group checks `GET /`. `GET /health` is also available. Keep both free of database calls.
- Use Better Auth for authentication and Drizzle for PostgreSQL persistence and migrations.

Infrastructure is Terragrunt and OpenTofu in `infra/`. The units are in `infra/applications/modules` and the Terraform modules they use are in `infra/modules`, copied from Sansoni's `devops-terraform-modules`. See `infra/README.md`. The current environment is `develop` in AWS account `806968064090`, region `ap-southeast-2`. ECS Fargate runs behind an ALB and uses Aurora PostgreSQL. There is no Redis and no message queue. The `develop` environment uses `asgi.pajamaprofits.net`, which is an internal staging domain. The production domain is not decided yet.

The deploy workflow in `.github/workflows/main.yml` and `taskdef.json` follows Sansoni's empireone pattern and uses their shared actions from `devops-github-workflows`. It runs only on pushes that change API files or the listed build and deploy inputs. `main` deploys to `develop`, which is staging, and `production` deploys to production. Pull requests run CI without deploying. `.github/workflows/infra.yml` plans `infra/` on pull requests and applies it on pushes to the same two branches.

Never run `terragrunt apply` or deploy without the user asking. The AWS account belongs to Sansoni, and Rodney reviews changes to `infra/`. Read-only AWS calls use the `sansoni` AWS profile. The target group checks `/`, which the API answers without a database call.

## Commands

Run these from the repository root.

- `npm start` — start the Expo dev server
- `npm run ios` / `npm run android` — run on a simulator or emulator
- `npm run api:dev` — start the API with reload on save
- `npm run lint` — ESLint
- `npm run typecheck` — type check with no emit, in every workspace
- `npm test` — Jest for mobile, Node test runner for the API
- `npm run format` — Prettier write
- `npm run e2e` — Maestro smoke test on the booted simulator or emulator (`npm run e2e -- web` for web). Needs Metro running. See the `device-testing` skill.

## Conventions

- In the mobile app, keep each feature self-contained under `apps/mobile/src/features/<name>`. Shared clients and helpers live in `apps/mobile/src/lib`.
- Use TanStack Query for anything fetched from the backend. Keep Zustand for session and UI state only.
- Never put secrets in the repo. Use EAS secrets or environment variables for anything sensitive.
- Match the existing style. Read the neighbouring code before adding to it.

## Delivery workflow

- Delivery scope and sequencing live in Linear, in the [Studio] Master App project and its documents.
- Work on a branch named after the Linear issue (`stu-<n>-<slug>`), with one PR per change. Never push to `main` or merge a PR: merging to `main` deploys to `develop`.
- Run `npm run lint`, `npm run typecheck` and `npm test` from the repository root before opening a PR.
- Where a requirement is ambiguous, state the reading you took in the PR and on the issue. Where it needs a product decision, set out the options on the issue rather than choosing silently.
- Check UI changes on a device, not only in typecheck or the web build.
- Don't change signing, the bundle ID or the Apple team without asking.
- Test with synthetic members only. Member data never goes in commits, logs, fixtures or PRs.

## Product context

Use the native `linear` CLI for Linear work. A repository-root `.linear.toml` can select this repository's workspace using its `workspace` setting; `linear auth login` stores the key in the system keyring. See `docs/linear.md`. Verify the workspace before accessing the backlog; do not assume the global default is this project's workspace.

Product requirements and feature specifications live in `docs/`; feature behaviour and acceptance criteria belong in `docs/features/`. Start with its index and the linked high-level designs. Carry existing agreements forward and keep unresolved product questions explicit rather than restarting architecture selection.

Everything under `docs/` MUST be evergreen: describe the current product requirements, decisions, constraints and operating procedures, not change history, implementation progress, dated handoffs, delivery plans or test-run reports. Do not duplicate facts reflected in implementation or code, including dependency versions, schema/route inventories, configuration defaults, copied code, resource names or command lists. Link to the authoritative implementation where needed. Keep delivery sequencing, accounting and verification evidence in Linear, PRs and thread artifacts outside `docs/`.

Agents must maintain the relevant feature specification as they work. Each fact has one canonical home; link to it instead of copying it across feature specs, HLDDs and overview pages. Distinguish required behaviour from implementation detail and unresolved decisions from agreed requirements. Review delegated work for both feature correctness and compliance with these documentation rules.
